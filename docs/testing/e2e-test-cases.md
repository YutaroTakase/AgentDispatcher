# E2Eテストケース

## 1. 目的

実際のGitHubリポジトリ、GitHub Issue、ChatGPT認証済みCodex CLIを使用し、AgentDispatcherの主要な利用経路と異常系を実機で確認する。

## 2. 前提条件

- [導入試験手順](installation-test-procedure.md)の必須項目が合格している。
- AgentDispatcherの管理画面へ `http://localhost:5088` でアクセスできる。
- `agent-dispatcher-worker` でGitHubとCodexへ認証済みである。
- E2E専用または破棄可能なGitHubリポジトリを用意する。
- 試験中に作成・変更するIssue、ブランチ、ファイルを本番開発へ混入させない。
- 推論モデル識別子と推論レベルには、試験時点のCodex CLIで実際に利用可能な値を設定する。

Codexの認証状態は次で確認する。

```bash
sudo -iu agent-dispatcher-worker codex login status
```

## 3. 試験用プロジェクトの準備

E2E専用リポジトリには、Codexが安全に読み取れる最小構成を用意する。

例:

```text
README.md
AGENTS.md
```

`AGENTS.md` には試験中に外部サービス、秘密情報、本番資産へ触れないことを明記する。

AgentDispatcherへ次の例でプロジェクト登録する。

```text
表示名: E2E Test
GitHubリポジトリ: <owner>/<repository>
既定ブランチ: main
Issue確認間隔: 5分
最大同時実行数: 1
実行履歴保存日数: 30
失敗時作業ツリー保存日数: 0
Issue検索条件: label:agent-dispatcher-e2e
最大候補数: 10
既定の推論モデル: 試験時に利用可能なモデル
既定の推論レベル: medium
```

試験用ラベルとして最低限次を用意する。

```text
agent-dispatcher-e2e
route-high
blocked
```

## 4. 必須テストケース

### E2E-001 プロジェクト登録と状態確認

**目的:** 登録時のGitHub到達確認とプロジェクト状態確認を検証する。

**手順:**

1. E2E用リポジトリをプロジェクト登録する。
2. プロジェクト詳細を再表示する。
3. 「実行環境」を開く。
4. 対象プロジェクトのリポジトリ、既定ブランチ、作業ツリー保存先を確認する。

**期待結果:**

- 登録が成功する。
- 保存した設定が再表示される。
- リポジトリと既定ブランチへ到達可能と表示される。
- 作業ツリー保存先が書き込み可能と表示される。

### E2E-002 Issue取得と既定の推論設定

**目的:** Issue取得条件と既定の推論設定を検証する。

**準備:** `agent-dispatcher-e2e` ラベルだけを付けた未完了Issueを1件作成する。Issue本文は「リポジトリのREADMEを読み、内容を要約してください。ファイルは変更しないでください。」程度の安全な内容とする。

**手順:**

1. プロジェクト画面で「今すぐIssue確認」を実行する。
2. 実行履歴を開く。
3. 対象Issueの実行詳細を確認する。

**期待結果:**

- 対象Issueが1件だけ実行待ちへ追加される。
- 既定の推論モデルと推論レベルが保存される。
- 状態が「待機中 → 準備中 → 実行中 → 成功」と遷移する。
- Issue専用作業ツリーでCodexが実行される。
- 最終結果、標準出力、標準エラー出力、開始・終了時刻を確認できる。
- 成功後に不要な成功作業ツリーが残らない。

### E2E-003 ラベルによる推論設定切替

**目的:** 優先順位付きの推論モデル選択規則を検証する。

**準備:**

1. `route-high` を必須ラベルとする選択規則を作る。
2. 既定設定と異なる推論モデルまたは推論レベルを規則へ設定する。
3. `agent-dispatcher-e2e` と `route-high` を付けたIssueを作成する。

**手順:**

1. 「今すぐIssue確認」を実行する。
2. 対象実行の詳細を確認する。

**期待結果:**

- 規則で指定した推論設定が選択される。
- 実行履歴へ採用した規則と推論設定が保存される。
- 後から規則を変更しても過去実行の推論設定は変化しない。

### E2E-004 同一Issueの二重実行防止

**目的:** 同じIssueを同時に複数実行しないことを検証する。

**手順:**

1. 対象Issueを手動で実行待ちへ追加する。
2. 状態が終了する前に同じIssueを再度手動実行する。
3. 「今すぐIssue確認」からも同じIssueを再検出させる。

**期待結果:**

- 2件目の実行は作成されない。
- 実行対象外となった理由を確認できる。
- 同一プロジェクト・同一Issueの有効な実行は最大1件である。

### E2E-005 最大同時実行数

**目的:** プロジェクトの最大同時実行数を検証する。

**準備:** 最大同時実行数を1に設定し、対象Issueを2件用意する。

**手順:**

1. 1件目を実行中にする。
2. 2件目を手動または定期確認で実行対象にする。

**期待結果:**

- 同時にCodex実行されるのは1件だけである。
- 上限到達中の候補について理由を確認できる。
- 1件目終了後に、次回確認で2件目を実行できる。

### E2E-006 実行取消

**目的:** 実行中Codexを管理画面から停止できることを検証する。

**準備:** 十分に時間のかかる安全な試験Issueを用意する。外部サービスや本番資産へ変更を加える内容は使用しない。

**手順:**

1. Issueを開始し「実行中」になることを確認する。
2. 実行詳細から取消を実行する。
3. systemd上の該当Codex一時サービスと実行履歴を確認する。

**期待結果:**

- Codexプロセスが停止する。
- 実行状態が「取消済み」になる。
- 取消後に「実行中」の状態が残らない。

### E2E-007 サービス再起動と実行状態復旧

**目的:** AgentDispatcher再起動後に不正な実行状態を残さないことを検証する。

**手順:**

1. Codex実行中のExecutionを1件作る。
2. `agent-dispatcher-worker.service` を再起動する。
3. AgentDispatcherの復旧処理と実行履歴を確認する。

```bash
sudo systemctl restart agent-dispatcher-worker.service
journalctl -u agent-dispatcher-worker.service -n 200 --no-pager
```

**期待結果:**

- 実プロセスが存在するExecutionは継続中として認識される。
- 実プロセスが消失したExecutionは永続的に「実行中」のまま残らず「失敗」へ確定する。
- 「準備中」のまま中断したExecutionも復旧処理で確定する。

### E2E-008 実行履歴とログ

**目的:** 実行結果の検索と証跡保存を検証する。

**手順:**

1. 成功、失敗、取消済みのExecutionを用意する。
2. 実行履歴でプロジェクト、状態、推論モデル、起動方法、日付範囲を使って絞り込む。
3. 各実行の詳細を開く。

**期待結果:**

- 絞り込み条件に一致するExecutionだけが表示される。
- 状態遷移、推論設定、所要時間、終了コード、最終結果、失敗概要を確認できる。
- 標準出力と標準エラー出力を確認できる。
- ログ本体はSQLiteへ無制限に保存されず、ファイルとして管理される。

## 5. 異常系テストケース

### E2E-009 GitHub認証異常

**目的:** GitHub未認証時に新規実行しないことを検証する。

**実施方法:** E2E専用環境でのみ、専用実行利用者を一時的にGitHub未認証状態にする。

**期待結果:**

- 実行環境画面でGitHub認証が異常になる。
- 新規Issue実行を開始しない。
- 既存の実行履歴は失われない。
- GitHub再認証後に状態確認が正常へ戻る。

### E2E-010 Codex認証異常

**目的:** Codex未認証時に新規実行しないことを検証する。

**実施方法:** E2E専用環境でのみ、専用実行利用者を一時的にCodex未認証状態にする。認証状態は `codex login status` で確認する。

**期待結果:**

- 実行環境画面でCodex認証が異常になる。
- 新規Codex実行を開始しない。
- 既存のプロジェクト設定と実行履歴は保持される。
- ChatGPTへ再度サインインした後に正常へ戻る。

### E2E-011 GitHub接続異常

**目的:** GitHubへ到達できない場合に新規実行しないことを検証する。

**実施方法:** E2E専用環境で一時的にGitHubへの通信を遮断するか、到達不能な試験リポジトリ設定を使用する。

**期待結果:**

- 状態確認が異常になる。
- 新規実行を開始しない。
- 既存Codex実行をGitHub一時障害だけで不必要に停止しない。

### E2E-012 失敗時作業ツリー保持

**目的:** Codex実行失敗時の調査用作業ツリー保持を検証する。

**準備:** 失敗時作業ツリー保存日数を1日以上へ設定し、安全に失敗する試験Issueを用意する。

**期待結果:**

- Executionが「失敗」になる。
- 失敗概要とログを確認できる。
- 対象作業ツリーが設定された保存期間中は残る。

## 6. 保存期間テスト

### E2E-013 定期整理

**目的:** 保存期限を超えた履歴、ログ、作業ツリーだけが整理されることを検証する。

保存期限は日単位のため、実時間で待機するか、E2E専用環境のSQLiteデータをバックアップした上で試験対象日時だけを過去へ変更して実施する。後者を行う場合は、本番データでは絶対に実施しない。

**期待結果:**

- 期限を超えたAgentDispatcher固有データだけが削除される。
- 実行中の資産は削除されない。
- GitHub上のIssue、ブランチ、Pull Request、コミットは削除されない。
- 整理結果と失敗理由を管理画面またはログから確認できる。

## 7. 合格基準

MVPの実機受け入れでは、E2E-001〜E2E-008を必須とする。

E2E-009〜E2E-013は異常系・運用確認として実施し、失敗がMVP要件へ直接影響する場合はリリース前に修正する。

各テストケースについて次を記録する。

```text
ケースID:
実施日時:
対象commit:
結果: PASS / FAIL / BLOCKED
Execution ID:
Issue番号:
確認内容:
証跡:
備考:
```
